**Verdict: run it, with small fixes.** The code is sound. I traced the two-phase `ConfirmedExchange`, the re-evaluation's world draws, the lesion and the projection, and found no bug that would waste the hour. The rule needs one change before the run: the refit-SD gate at three refits is close to a coin flip and is stricter than the registered reliability rule, so outcomes (ii) and (iii) would partly be decided by luck. Two records are missing that you would need afterwards, V2 is predictable from the existing records, and the CUDA preflight for the new stage has not been run into the real preflight directory.

## 1. The rule and the variants

1. **High. The SD ≤ p/2 gate with three refits does not discriminate.** `scripts/e03a.py:1233-1234`, PILOT-DEV §7 "reliable". For n = 3, s/σ has a 95% range of about 0.16 to 1.92. A true refit SD of 0.59p (pilot-dev's own MIP/URXL value) passes the gate about half the time. A true SD of 0.75p passes about a third of the time. Over four variants, the unchanged search would pass the SD half of "reliable" somewhere with probability near 0.9. It is also inconsistent with the registered rule: DESIGN §6 line 280 makes per-brain reliability "SD at most 2 δ_search", which with pilot-dev's δ_search is 0.86p, so a variant can fail the check's gate while being reliable under the design. Fix: gate on the restoration comparison alone (mean of the three refits equivalent to or above exact restoration), and if you want a dispersion guard, require that no single refit is "below" restoration. That uses the world bootstrap, whose half-width is about 0.03, instead of an SD from three numbers. Report the SD with its interval, roughly 0.52s to 6.3s.

2. **Medium. "Recovers" on URXL is mostly a lottery on its two gap partners.** `wormwars/e03a/null.py:152` averages the three types' AUCs with equal weight. URXL has 18 in, 25 out and 2 gap partners. Under the null the gap AUC has SD near 0.2 against about 0.07 and 0.06 for in and out, so the gap type carries about four fifths of the statistic's null variance. The null SD of the mean is about 0.075. Reaching p < 0.0125 needs a mean AUC near 0.67. In and out at 0.70 each with gap at chance gives p near 0.04 and reads as (ii). This is the registered statistic, so keep it as the gate, but §7 should say this, and the record should carry the per-type null mean and per-type p. `N.recovery` already returns the per-type nulls from the bank; it costs nothing.

3. **Medium. V2 is predictable from the records and nearly wasted.** Acceptance at d ≥ 0 is unconditional at any temperature. With offspring-minus-current means of −0.15 to −0.20 and SDs of 0.36 to 0.42 (`full.json:35182` onward), the best of eight scores at or above the current state almost every generation, which is why `accepted_moves` of 123 to 146 equals 400 replica-generations times one third. A colder ladder changes only the rare d < 0 case and the swap dynamics, and tune round A already showed a tenfold range of T₁ made no difference. I would spend its 0.46 M episodes on three random-partner refits each for V3 and V4 (about 0.6 M episodes, 0.28 h). Outcome (ii) says "the search can restore function with the true partners", which means little without the advantage over strata-matched random partners under the new search. The total would be about 2.3 M episodes, about 1.1 h, still inside 1.42. If V2 stays, read it as a control, not a candidate.

4. **Medium. Variant order.** `scripts/e03a.py:1294` runs V1, V2, V3, V4. A cap stop loses V3 and V4, the two both reviewers asked for. Reorder to V4, V3, V1, V2 at no cost.

5. **Low. Thresholds I would keep.** T = 0.01 for the single chain is fine: at 64 worlds a one-count loss is accepted 21% of the time, so it is near-greedy with a small tolerance. Bonferroni over four is valid. A fixed-sequence test (V4, V3, V1, V2, each at 0.05, stop at the first failure) would be more powerful for the favoured variants, if the owner accepts declaring the order now.

6. **Low. Missing for reading (ii) and (iii).** The acceptance rate is not written for V1 to V3: `_diagnostics` (`scripts/e03a.py:650-663`) writes `accepted_moves` but not `trace.accepted`, which is why D313 had to infer acceptance. Write the per-generation share accepted. The no-task control costs no simulation (`scripts/e03a.py:742-750`) and should run per variant, since V3 and V4 change the proposal structure.

## 2. The code

7. **`ConfirmedExchange` inside `run_lockstep` is correct.** `wormwars/e03a/search.py:337-375`. Phase one stores the candidates without touching `generation`, so `done` is unchanged and the loop re-asks. `check()` runs before both evaluations. Each variant is its own batch, so no out-of-phase mixing. `take` indexes `cat([current, candidates])` correctly, swaps use the confirmation scores, and the trace has one `paired` entry and one `scores` entry per generation. Two notes. For V4, `trace.scores` holds confirmation-world scores, so its `cold_score_sd_over_generations` is not comparable to V1 to V3's. The docstring at line 324 overstates: a candidate with no true gain is rejected about half the time, not "usually".

8. **The `tell` split.** `search.py:255-312`. From the code as it stands the draw order is unchanged: R acceptance draws, then the swap draws, with the pending and paired handling moved intact. I could not diff against the previous commit in this session. A cheap bitwise check exists: `runs/e03a-smoke/pilot-dev/records/full.json` was written at `4260dad` on 2026-10-17. Rerun the CPU smoke pipeline at `1877a05` into a temporary directory and diff `per_search[].cold_score_series`, `paired_series` and `pair_rates` for `tune` and `full`.

9. **Re-evaluation world draws and truth block are correct.** `scripts/e03a.py:1165-1167`, `1182-1202`. Selection ids are keyed on start, size and set, so they are independent across sets and sizes, and the select, truth, search and final ranges are disjoint. The reshape to [sets, 9, worlds] matches the concatenation order. Moves are off for `refit-0` and on for `free-0`. PILOT-DEV §1 still says the ids run to 1 482 799 999; the check uses up to 1 482 909 999, so amend §1. Two small improvements: store the raw `sel` and `t_mean` arrays per set (a few hundred numbers), and note that `share_accepted_truly_worse` is P(accepted and worse) over sets while §7's wording reads as P(worse given accepted). Nesting the selection worlds (16 within 32 within 64) would pair the size comparison; with 16 sets the winner's mean true gain resolves to about ±0.025, which is marginal against effects of a few hundredths.

10. **The lesion is correct, gap edges included.** `scripts/e03a.py:1127-1162`. A gap lesion clears the mask that `Reinsertion.genome` writes to the single undirected position (`reinsert.py:217`), so both sides go. The restoration is re-scored in the 46-state batch outside `replay_mode()`, so `restored_mean` may differ slightly from baseline's. That is fine for a paired drop, but the record should say so.

11. **Projection arithmetic verified.** 1 664 000 search, 327 168 re-evaluation and 159 744 final episodes sum to 2 150 912. At the slower of tune's and full's rates plus finals at 972 per second this is 0.99 h. `full`'s timing shows a fixed cost near 1.1 s per rollout (72 × 16 batches ran at 448 per second against 708 for 540 × 16). The check's batches are 1 024 to 4 608 episodes, so I expect 0.9 to 1.0 h. It fits with about 0.4 h of slack.

12. **Medium, procedural. The CUDA preflight for the new stage has not been run where it counts.** `runs/e03a-smoke-cuda/pilot-dev/records/` has no `search-check.json`. The gpu test writes to a temporary directory. §1 requires the preflight before GPU budget, and `PilotClock` reads that directory's compute record. Run the stage with `--smoke --device cuda` first.

13. **Record completeness, rule 5.** The variant row (`scripts/e03a.py:1315-1329`) omits `ranking` and `final_counts`, which `full`'s row writes. The enrichment's input would then live only in the local npz.

## 3. Wording in §7

14. Outcome (ii) "cannot find them here" should be "did not find them above chance at this budget". The lesion "asks whether the original partners' contribution sits on a few edges" measures the MIP brain's dependence on each of X's edges, which is related to the 0.12 advantage but not the same quantity. "What it cannot show" should add: no random-partner refits, so the identity advantage under a new search is unmeasured (unless finding 3 is taken); the enrichment statistic on URXL is dominated by two gap ranks; and the three-refit SD, if it stays in the rule.
